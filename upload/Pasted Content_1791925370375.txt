# Product Requirements Document
## Bilingual Online Menu SaaS

**Product Type:** Multi-tenant SaaS  
**Primary Languages:** Persian (RTL) + English (LTR)  
**Target Businesses:** Restaurants, cafés, fast-food restaurants, bakeries, juice bars, hotels, food courts, catering businesses, and similar food-service businesses  
**Platforms:** Web, PWA, Mobile Web  
**Primary Access Method:** QR Code + direct URL  
**Architecture:** Multi-tenant SaaS  
**Initial Deployment:** Single-instance capable, horizontally scalable

---

# 1. Product Vision

Create a modern SaaS platform that allows food-service businesses to create, manage, customize, and publish a professional online menu without requiring technical knowledge.

Each business receives its own public menu URL and QR code.

Example:

```text
https://menu.example.com/cafe-nova
```

Customers scan the QR code at the table and immediately see the restaurant's menu.

The system must support:

- Persian and English content
- RTL/LTR interfaces
- Categories and menu items
- Images
- Prices
- Variants
- Add-ons
- Availability
- Dietary information
- Search
- Featured items
- Promotional items
- Restaurant branding
- QR codes
- Analytics
- Multi-tenant administration
- Multiple branches
- Role-based access control

The product should feel closer to a **digital storefront** than a simple PDF menu.

---

# 2. Problem Statement

Traditional restaurant menus have several problems:

- Printing is expensive.
- Price changes require reprinting.
- Customers cannot easily switch languages.
- PDF menus are often difficult to navigate on mobile.
- Menu images may be low quality.
- Restaurants have no useful analytics.
- Different branches may have different menus.
- Updating availability is inconvenient.
- QR-code menus are often visually poor.
- Restaurants usually need a developer to make significant changes.

The SaaS should solve these problems with a simple management dashboard and a fast mobile-first customer experience.

# 3. Goals

## Primary Goals

1. Allow a business to create a digital menu in minutes.
2. Allow menu content to exist independently in Persian and English.
3. Provide automatic RTL/LTR rendering.
4. Provide a mobile-first customer experience.
5. Generate QR codes automatically.
6. Allow restaurants to update prices and availability instantly.
7. Support multiple branches.
8. Support restaurant branding.
9. Provide basic analytics.
10. Provide subscription-based SaaS billing.
11. Support future languages without redesigning the data model.

## Secondary Goals

- PWA installation
- SEO-friendly public menus
- Social sharing
- WhatsApp/Telegram sharing
- Table-specific QR codes
- Promotional campaigns
- Ordering integration in future versions
- POS integration
- Digital signage

---

# 4. Non-Goals

The first version should NOT attempt to become a complete restaurant POS.

Out of scope for MVP:

- Full accounting
- Inventory management
- Kitchen Display System
- Employee payroll
- Delivery fleet management
- Payment processing
- Full online ordering
- Reservation management
- Loyalty program
- Advanced CRM

These can become future modules.

# 9. Bilingual Content Model

Every translatable entity should store language-specific fields.

Example:

```json
{
  "name": {
    "fa": "چیزبرگر",
    "en": "Cheeseburger"
  },
  "description": {
    "fa": "برگر گوشت با پنیر چدار",
    "en": "Beef burger with cheddar cheese"
  }
}
```

Do NOT create separate products for each language.

Instead:

```text
MenuItem
 ├── name.fa
 ├── name.en
 ├── description.fa
 └── description.en
```

This keeps both language versions tied to the same product.

Example:



# 57. RTL Requirements

Persian interface must support:

```css
direction: rtl;
```

But the system should NOT simply mirror everything.

Elements such as:

- numbers
- prices
- phone numbers
- email
- URLs
- maps
- technical identifiers

may need LTR rendering.

Use logical CSS properties:

```css
margin-inline-start
padding-inline
border-start-start-radius
```

rather than:

```css
margin-left
padding-right
```

where appropriate.

# 81. Design Principles

The product should follow these principles:

### 1. Mobile First

The customer is probably standing at a restaurant table using a phone.

### 2. Fast

The menu should open almost immediately.

### 3. Visual

Food photography should be a first-class component.

### 4. Simple

Restaurant staff should not need technical knowledge.

### 5. Bilingual by Design

Persian and English should not be an afterthought.

### 6. Multi-Tenant by Design

Tenant isolation must exist at the architecture and database levels.

### 7. API First

Future POS, ordering, mobile apps, and integrations should be possible.

### 8. Extensible

The menu should become the foundation for future restaurant services.

# 83. Final MVP Definition

The first production release is successful when a restaurant can go from:

```text
"I have no digital menu"
```

to:

```text
"I have a professional bilingual menu
with a QR code that my customers can scan"
```

in **less than five minutes**, without developer assistance.

The customer experience should be:

```text
SCAN → OPEN → CHOOSE LANGUAGE → BROWSE
```

while the restaurant experience should be:

```text
LOGIN → EDIT → PUBLISH → PRINT QR
```

The product's core competitive advantage should be the combination of:

**extreme simplicity + excellent mobile UX + native Persian/English support + multi-tenant SaaS architecture + instant publishing.**
